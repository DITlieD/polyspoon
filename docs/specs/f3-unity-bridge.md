# F3 local Unity authoring

The installable `com.openpoly.workshop` package adds `Window > Polyspoon`. A local Node executable and source checkout are configured in the window. The package uses the existing TypeScript catalog, parameter validation and GLB exporter. Geometry stays in TypeScript.

Inputs are a versioned JSON request on stdin: catalog discovery, or a family with optional preset and typed parameter overrides, or a saved design. One process handles one request. Requests, output, elapsed time and diagnostics are bounded. No shell, network listener, downloaded dependency or submitted code execution is involved.

The window lists all twelve registered recipes and their presets. Numeric, integer, choice, toggle and color controls come from catalog metadata. Build creates a serialized scene root. Rebuild targets the selected root, including selection of one of its descendants.

The root stores canonical design JSON, recipe/version, source hash and current generated child. Rebuild replaces only that child. Root transform, custom components and separate user children survive. Direct edits inside the generated subtree are regenerated. Each successful create or rebuild is one Undo transaction. Versioned GLB assets retain imported meshes and materials, including versions referenced by Undo. Scene save/reopen must retain the design and asset references.

Parsing, validation, process failure, timeout, cancellation and import failure leave the existing root and child unchanged. Window close, assembly reload and Editor exit cancel active work and release its process and temporary state. The manifest declares glTFast 6.20.0 and minimum Unity 6000.0. Testing covers Unity 6000.5.5f1 with URP 17.5.0 and glTFast 6.20.0. The minimum declaration is not verification of other versions. The configured local checkout must be trusted; process bounds do not make it a sandbox for untrusted generators.

## Saved-design compatibility

A build request containing a saved design runs through `loadDesign` before generation. Its validated migration notice remains in both `response.design` and the GLB root configuration metadata. Old colored cottage designs and their validated current forms produce the same canonical configuration, appearance, geometry and GLB as the existing CLI exporter. Default and fresh builds remain notice-free. A forged notice fails before emitting a response or partial asset. Protocol version 1 and its mutually exclusive saved-design versus family/parameter inputs remain unchanged.

## Canonical selected-root editing

Protocol 1 retains strict catalog/build requests and the existing exclusion between saved design and family/preset/parameters. A strict `resolve` request takes a saved design and returns its `loadDesign` canonical design and source hash without a geometry report or GLB export. A saved-design build may additionally contain `edits`, restricted to the current recipe's control keys. Edits without a saved design, unknown controls, appearance, version and migration overrides fail without partial output. The bridge validates the saved baseline first, combines its canonical design input with control edits, recomputes applied values and exports through `buildAsset`, retaining validated migration and baseline appearance.

Selecting a generated scene root resolves its versioned design before enabling fields or rebuild. The window keeps that canonical baseline separate from current control values. It submits only changed control values as explicit edits. Defaults or presets within the same selected recipe retain saved appearance/history; choosing a different recipe explicitly starts fresh creation and disables rebuilding that selected root. That recipe choice retains the already observed Unity selection identity; a delayed unchanged-selection callback cannot cancel fresh creation. Deselecting starts fresh defaults. Invalid saved roots stay uneditable and cannot silently become fresh rebuilds. An explicit recipe choice can start a new asset without repairing the invalid root.

Every async request captures its cancellation source, selection revision and active scene. Scene identity is stored and compared as a Scene value without integer handle conversions. Selection changes invalidate previous results and cancel prior work. Resolving or building checks the selected root and its serialized design before applying a response. New-root creation suppresses only its own synchronous selection callback, then adopts the returned root/design. Undo and Redo use the guarded selection refresh, including when the restored design stays on the same selected root. If root, serialized design and scene are unchanged, pending control edits are retained. Closing the window invalidates outstanding callbacks. Completion only releases its own operation and updates controls; it does not recursively resolve selection. A failed or cancelled resolve is not automatically retried. Reloading the catalog or selecting another root is an explicit retry.

Centimeter fields display meter inputs multiplied by 100 and store edits divided by 100. Degree controls use degree labels without scaling. Meter, ratio, integer, toggle, color and choice values keep existing engine units. Public menu/window/package documentation uses Polyspoon while compatibility package IDs, namespaces, serialized fields, EditorPrefs keys and GUIDs remain unchanged. Editor compilation and recorded fixture behavior checks have passed in the tested environment. Actual interactive window acceptance remains a separate pending check.
