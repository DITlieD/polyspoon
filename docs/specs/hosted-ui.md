# Hosted marketplace UI

F6-UI-1: build separate public and authenticated entries. Public landing, documentation and email-link sign-in import only public branding, promotional content and the deliberately public local toolkit setup. Disable Vite public-directory copying. Fail the public build on catalog, recipes, model previews or private metadata imports. Do not serve the existing local-editor dist as the public site.

F6-UI-2: request maintained Better Auth magic links, let the backend verify them and read current membership through `/api/me`. No simulated login, local-storage session, client authority or public admin bootstrap. Cookie requests use the same origin and no-store. On authentication loss clear private views and in-memory object URLs before returning to sign-in. Distinguish mail configuration/quota, membership restriction, request failure and empty results.

F6-UI-3: members browse/search published server models, inspect actual model metadata and private previews, download exact manifest-bound artifacts, vote and manage account/session/token controls. The UI hides irrelevant privileged navigation for usability; every operation remains backend-authorized. Contributor submission/status and moderator/admin actions use real supported endpoints. Missing API contracts are surfaced for coordination rather than simulated.

F6-UI-4: package private assets as a deterministic immutable file manifest, paths rooted at `/app/`, with no public fallback. Public distribution deliberately includes only approved brand/promo files and the current open-source agent bundle. Public and private outputs are distinct directories. Existing releases and local preview files stay unchanged.

F6-UI-5: tests first for API/session failure behavior and build isolation. Exercise actual local endpoints and maintained email verification in browser journeys after gateway wiring. Retain download integrity and anonymous private-byte denial evidence. Screens use supplied artwork, responsive accessible controls and meaningful loading/empty/error states. No deployment or provider writes belong to this UI task.

F6-UI-6: authenticated customization at `/asset/:version?edit=1` reuses Stage, ControlPanel and DesignSession. Enable only a published recipe whose exact recipe/version/delivery revision and uploaded source-package path, SHA-256, bytes and media type match the private build's trusted built-in registry. Build validation checks the approved archive, its complete local implementation source closure and pinned runtime dependencies. Submitted source is never imported or executed. Unsupported or mismatched identities retain static preview and verified downloads with an explicit unavailable message.

On entry, verify the immutable design and source archive once, compare the saved design to published metadata and reject migration or canonicalization differences. Shape/color edits remain in memory. Undo, redo, reset and edited-design reload retain the exact published origin. Edited GLB and bundled exports retain origin and license notices. Exports recheck the member session. Invalid controls disable export; session loss disposes the stage and design session. Browser evidence covers a trusted bench's geometry/material changes, export, reset/reload, wrong-origin reload rejection, identity denial and expired export. Other registered built-ins require their own functional review before claiming equivalent observed coverage.

F6-UI-7: full submissions keep the sealed subject and all files unchanged. Limits are 256 files including the report, 16 MiB total and 2 MiB per file, including zero-byte files. Fresh version progress supplies the server-owned receipt profile, uploaded/verified counts, completion and bounded pending/failed paths. After interruption and page reload, reselect the original folder and send the union of pending/failed paths once, skipping verified files. A successful upload requires a server verification receipt; failure refreshes authoritative progress. Enable submission only on server-confirmed completion, and refresh that decision before the existing transition request. Browser evidence uses the actual unchanged 194-file original bench run, interrupts delivery, reloads, resumes and submits without claiming processing or publication.
