# Reproducible review records

A sealed subject binds the literal request, canonical selected design and validated migration, recipe and delivery identity, exact source/lock/runtime snapshot, exercised control cases and views, terminal technical report, and all artifact/render bytes. It extends the existing recipe verification report. Canonical key ordering produces deterministic digests. The subject ID excludes itself. Write records with exclusive creation; changing evidence or repairing a run produces a new subject and preserves the old attempt.

Successful subject sealing accepts only a stable terminal successful run with passed stages and a complete matching inventory. A separate failed-attempt record retains terminal failed/cancelled results and first failure; it is never a successful subject. Validate current source and verification input hashes and every referenced artifact. Reject unsafe paths, symlinks, missing files, extra unlisted evidence, changed bytes, partial states and mismatched selected designs. Source package identity comes from its actual index and the shared delivery identity helper. Selected verification and render inputs retain the canonical migration notice; fresh preset captures stay notice-free.

Pinned dependency versions are bound alongside runtime, lock and exact source identity. Review categories are technical, visual, portability and executable-source. Executable-source records explicitly cover dependency, import, license, provenance and redistribution inspection without granting licenses. Each record binds the subject and artifact manifest, reviewer, decision, explicit coverage, findings and limits. Findings identify case, part, view and evidence from the subject. Failures require a defect and proposed correction. Uncertain, contradictory or uncovered findings cannot pass. A visual record is an authored observation, never an aesthetic grade derived from geometry metrics. Agent review is allowed in local authoring.

Publication eligibility consumes trusted records and principal capabilities supplied separately by the application authority. Uploaded subject or contributor JSON cannot grant a capability or install a trusted record. Reject missing, revoked/replaced, forged, stale, mismatched and self-authored reviews. Platform-controlled technical attestations are held separately from authored reviews. All required reviewers differ from the contributor. A qualified independent reviewer may cover visual, portability and executable-source categories; no reviewer-count rule applies. Keep technical, visual, portability, source/provenance and eligibility results separate.

The local CLI exposes seal, attempt, record, validate-record and eligibility endpoints. Passing source reviews reference the selected source ZIP. Passing portability reviews also reference the selected GLB and a separately hashed replay attachment. Failed or uncertain source reviews may declare partial inspection. Its result is local eligibility evidence only. An explicitly selected separate trusted-store fixture exercises authority decisions; it is not authenticated persistence or a deployed publication service. F6 must provide authenticated identities, server-owned records, publication transitions, storage and execution isolation. Bounded fixtures disclose their scope and cannot claim arbitrary-asset quality or actual publication.

Verification uses focused tests first, including deterministic identity, migration preservation, evidence tampering, missing/unsafe/symlink paths, failed/partial/stale runs, uncertain and contradictory findings, coverage gaps, capability violations, self-review, missing records and artifact replacement. Source-ready delivery includes bounded CLI fixtures and exact commands. Full recipe verification and original visual defect cases run only after the shared source freeze.
