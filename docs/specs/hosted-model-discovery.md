# Hosted individual model discovery

GET `/api/catalog` remains authenticated and requires `catalog:read` for scoped tokens. Interactive restricted members remain denied. The endpoint accepts optional `q`, `type`, `style`, `offset` once each. `q` is a case-insensitive title substring, trimmed, at most 100 characters. Empty type/style means all. Allowed type values derive from the same registered metadata projection used for classification and facets. Current presentation categories are `Props`, `Nature`, `Structures`, `Buildings`; `unclassified` selects unavailable type facts. Style values are `faceted-low-poly` and `unclassified`, reusing the existing website style authority. Unknown type/style values return 400 `invalid_catalog_type` / `invalid_catalog_style`; invalid or repeated parameters return 400 `invalid_catalog_query`. `offset` defaults to zero, accepts integers 0–100000, and invalid values return 400 `invalid_catalog_offset`.

Response is `{models,total,offset,limit:24,nextOffset,facets}`. Existing model fields remain `id,asset_id,title,kind,published_at,votes,voted`. Each row adds `type:string|null`, `style:string|null`, `metadataSource:"registered-recipe"|"unclassified"`, and `preview:{path,sha256,bytes,media_type}|null`. Model detail adds the same type/style/source fields. The existing detail delivery contract stays unchanged.

Type means recipe presentation category, not storage kind. Classification uses the sealed subject's recipe ID/version and selected design family/version only when they agree with an exact known registered recipe metadata entry. Type/category and style facts come from current recipe presentation and `src/site/discovery.ts`, not title guesses or bundle membership. Missing, inconsistent or unknown historical identities return null metadata and `unclassified`. Classification describes the identified registered recipe; it does not assert trusted executable package identity or grant editor activation. New families require the existing registration/integration process before classification.

Facets are `{types:[{value,label,count}],styles:[{value,label,count}]}`. Labels reuse current presentation categories and style labels, including `Unclassified`. Counts cover all currently eligible newest published models, independently of selected filters, so filter options stay stable. All known values, including unclassified, are present with zero counts when absent.

Filters combine with AND. List and total consider only the newest published version per individual asset. Ordering is `published_at` descending, then version ID descending, with null publication times treated as zero. `nextOffset` is `offset+24` when further matching rows exist, otherwise null. Offset beyond the result set returns an empty page and the correct total. UI resets offset to zero whenever q/type/style changes or Clear filters is used; it preserves the complete query on model/back links and browser reload. Concurrent publication or withdrawal can change totals and shift pages; the API does not retain a historical catalog snapshot. Each request rechecks current publication and membership.

Preview descriptors use the existing `selectPublicDelivery` selected-case preview rule. Listing never returns image/model bytes or public URLs. UI fetches the descriptor through the existing authenticated catalog file gateway and does not need a detail request for each card. No selected preview yields null; no arbitrary alternate-case image is substituted. Current review, withdrawal, delivery and eligible voter rules stay in force.

Migration 0009 stores an immutable versioned metadata projection of the registered recipe categories and existing website style authority. Server code reads that lightweight table; it does not import recipe geometry. The focused source-consistency check compares projected rows with registered recipe presentation and modelStyle facts. Registration/integration of future recipes must add their projection rows through a later migration; allowed types/facets then extend automatically. Implementation is limited to backend catalog metadata/query, that migration, and focused contract/HTTP verification. It does not modify immutable subject bytes, UI, trusted builds, recipe registration or rigging. Production blockers observed during this work are reported separately; this is not a deployment audit.
